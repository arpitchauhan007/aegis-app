# AEGIS — AI/Coding Rules

## 1. Core Rule
Build only what is defined in the PRD and Phases. Do not invent product behaviour, claims, integrations, providers, legal statements, or user data fields.

## 2. Source of Truth
Priority order:
1. Explicit user/project requirements.
2. PRD.md
3. Architecture.md
4. Rules.md
5. Phases.md
6. Design.md
7. Memory.md once coding begins.

When documents conflict, stop and identify the conflict instead of guessing.

## 3. Technology Rules
Prefer:
- TypeScript.
- React/Next.js.
- Semantic HTML.
- Tailwind CSS.
- Accessible component primitives.
- Zod validation.
- Established, maintained libraries.

Avoid:
- Unmaintained dependencies.
- Duplicate libraries solving the same problem.
- Custom UI primitives when an accessible primitive already exists.
- Direct DOM manipulation unless necessary.
- Any dependency that adds tracking by default.

## 4. Coding Standards
- Strict TypeScript.
- Small components.
- Single responsibility.
- Explicit names.
- No dead code.
- No duplicated constants.
- No hard-coded secrets.
- No production URLs embedded in random components.
- Reusable design tokens.
- Server-side validation for trusted operations.
- Client-side validation only as a usability layer.

## 5. Error Handling
- Never hide errors silently.
- Never expose stack traces/secrets to users.
- Use clear human-readable messages.
- Give the user a recovery action.
- Log technical details only on the server.
- Emergency workflows must fail safely and visibly.

## 6. AI Rules
AI is an assistant, not an authority.

AI may not:
- Diagnose.
- Prescribe.
- Claim medical certainty.
- Override consent.
- Override permissions.
- Invent sources, providers, prices, policies, statistics or testimonials.
- Create fake user stories.
- Pretend an alert was clinically verified.
- Send external actions without the required permission/confirmation.

For high-impact or safety-related actions, use deterministic rules and human acknowledgement.

## 7. Data Rules
- Collect the minimum data required.
- Every new field requires a stated purpose.
- Never add health/location data "for future use."
- Never send sensitive data to analytics.
- Do not expose data between family members without explicit permission/configuration.
- Do not expose provider information beyond what is required.
- Delete/retain according to documented policy.

## 8. Consent Rules
- Separate necessary processing from optional consent where applicable.
- Do not pre-check optional consent boxes.
- Do not bundle unrelated purposes into one optional checkbox.
- Make withdrawal/revocation understandable.
- Record the consent version and timestamp where required.
- Do not use "By using this website you automatically agree..." as a substitute for required consent.

## 9. Cookies & Tracking
- Essential cookies only by default where possible.
- Non-essential tracking must be reviewed for consent requirements before activation.
- No ad trackers in MVP.
- No session replay by default.
- Maintain a cookie/SDK inventory.
- The reject/decline path must not be intentionally harder than accept.

## 10. Accessibility Rules
Target WCAG 2.2 AA.

Every interactive element must have:
- Keyboard operation.
- Visible focus state.
- Clear accessible name.
- Logical tab order.
- Meaningful error feedback.

Every meaningful image needs appropriate alt text.
Decorative images should use empty alt text or equivalent semantics.
Never communicate important status using colour alone.

## 11. UI Rules
- Minimum practical touch targets: 48×48 CSS px.
- Prefer larger controls for primary actions.
- Body text should generally be 16 px or larger.
- Use short labels.
- Use icon + text for important actions.
- Keep navigation predictable.
- Avoid swipe-only controls.
- Avoid dense data grids on the primary user experience.
- Do not use flashing or unnecessary motion.

## 12. Content Rules
Remove:
- Fake reviews.
- Fake testimonials.
- Unsupported awards.
- Unsupported numbers.
- Fake partner logos.
- Fake user counts.
- False urgency.
- "100% safe/secure" claims unless legally and technically substantiated.

Prefer:
- Specific, verifiable statements.
- Clear limitations.
- "Designed to..." rather than guaranteed outcomes.

## 13. Image/Asset Rules
Before production:
- Confirm ownership/license.
- Record source and license.
- Do not copy protected marketing images without permission.
- Do not use identifiable people as "AEGIS users" unless authorised.
- Provide suitable alt text.

## 14. Forms
Every input must have:
- Persistent visible label.
- Appropriate autocomplete/input type.
- Keyboard access.
- Clear required/optional state.
- Inline validation.
- Accessible error association.
- No placeholder-only labels.

Forms collecting optional data must explain why it is needed.

## 15. Legal Pages
Do not fabricate legal entity names, addresses, registration numbers, refund terms, retention periods, jurisdiction clauses, DPO details, or regulatory certifications.

Use placeholders until verified.

## 16. Testing Gate
Before declaring a feature complete:
- Typecheck.
- Lint.
- Unit/integration tests where relevant.
- Keyboard test.
- Screen-reader/semantic check.
- Contrast check.
- Mobile/tablet responsive check.
- Empty/loading/error-state check.
- Permission/authorization check.
- Privacy/data-flow check.
- No unsupported claims.
- No accidental third-party tracker.

## 17. Stop Conditions
The coding agent must stop and ask for clarification when:
- A requirement is legally ambiguous.
- A medical/safety decision is being introduced.
- A feature requires sensitive data not in the PRD.
- A third-party integration would materially expand data sharing.
- A payment/refund rule is unknown.
- A business/legal identity is missing.
- A claim cannot be supported.
