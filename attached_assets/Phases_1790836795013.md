# AEGIS — Build Phases

## Phase 0 — Foundation, Compliance & Design System
**Goal:** establish the rules before feature coding.

Deliver:
- Repository setup.
- TypeScript/Next.js project.
- Lint/typecheck/test setup.
- Design tokens.
- Responsive breakpoints.
- Accessibility baseline.
- Legal-page route placeholders.
- Privacy/cookie/terms/refund content data model.
- Consent model.
- Analytics disabled by default.
- Asset/licensing register.

Exit criteria:
- Build runs.
- Design system is reusable.
- No hidden analytics/tracking.
- Core accessibility checks pass.

## Phase 1 — Public Website
Build:
- Landing page.
- AEGIS explanation.
- Supported use cases.
- Business/contact information.
- Privacy Policy.
- Terms & Conditions.
- Cookie Policy.
- Refund/cancellation page if applicable.
- Accessibility statement/page.
- Cookie preferences.

Exit criteria:
- No fake reviews.
- No unsupported claims.
- All images have known licensing status.
- Legal links are visible.
- Forms are keyboard accessible.

## Phase 2 — Authentication & User Setup
Build:
- Sign-up/login.
- User role selection.
- Minimal onboarding.
- Trusted contacts.
- Consent/notice flow.
- Accessibility preferences.
- Language preference structure.

Exit criteria:
- Authentication is secure.
- Required/optional consent is separated.
- No unnecessary profile data is collected.

## Phase 3 — Elder Home / Dashboard
Build:
- Today card.
- Check-in.
- Family shortcuts.
- Help/service shortcuts.
- Emergency/help button.
- Reminder states.
- Loading/empty/error states.

Exit criteria:
- First-time user can understand primary actions without documentation.
- Keyboard and touch navigation work.

## Phase 4 — Family Connection
Build:
- Family list.
- Call/message actions.
- Communication routine.
- Permission-controlled status sharing.
- Notification preferences.

Exit criteria:
- No unauthorised information exposure.
- Permission boundaries tested.

## Phase 5 — Help & Service Requests
Build:
- Service categories.
- Request form.
- Provider listing.
- Request tracking.
- Confirmation and acknowledgement.
- Manual fallback.

Exit criteria:
- Every request has a visible state.
- Provider information is verified or clearly marked.
- No invented service availability.

## Phase 6 — Check-In & Escalation
Build:
- Scheduled check-ins.
- Missed-check-in rules.
- Escalation chain.
- Acknowledgement tracking.
- Notification delivery state.

Exit criteria:
- Escalation is deterministic.
- Failure states are handled.
- AI is not required for safety-critical routing.

## Phase 7 — Emergency Workflow
Build:
- Emergency/help entry point.
- Configurable contacts.
- Alert creation.
- Acknowledgement.
- Escalation.
- Audit events.

Exit criteria:
- Clear limitation that AEGIS is not a replacement for local emergency services.
- Test emergency and failure scenarios.

## Phase 8 — Optional AI Assistance
Build only after deterministic workflows are stable:
- Natural-language request parsing.
- Voice/text assistance.
- Request classification.
- Plain-language summaries.

Exit criteria:
- AI cannot bypass permission controls.
- AI outputs have fallbacks.
- No medical diagnosis/prescription.
- No fabricated information.

## Phase 9 — Privacy, Security & Compliance Audit
Review:
- Data inventory.
- Consent records.
- Cookie/SDK inventory.
- Third-party processors.
- Retention/deletion.
- Access control.
- Audit logs.
- Legal pages.
- Business details.
- Refund rules if paid.

Run:
- Dependency/security scan.
- Accessibility audit.
- Keyboard test.
- Contrast test.
- Mobile/tablet test.
- Form test.
- Privacy flow test.

Exit criteria:
- No unresolved critical privacy/security/accessibility issue.

## Phase 10 — Pilot / Usability Testing
Test with representative users across the target age range.

Measure:
- Task completion.
- Time to find help.
- Navigation errors.
- Font readability.
- Button comprehension.
- Check-in completion.
- User confidence.

Fix usability issues before adding more features.

## Phase 11 — Production Readiness
Complete:
- Monitoring.
- Backups.
- Incident process.
- Support process.
- Privacy/contact process.
- Production legal review.
- Domain/email configuration.
- Final asset/license check.

## Memory.md Rule
Do **not** create Memory.md during initial setup.

Create Memory.md only after coding begins. It should record:
- Implemented features.
- Current architecture decisions.
- Database/schema changes.
- Known bugs.
- Current phase.
- Next work item.
- Deferred decisions.
- Relevant compliance decisions.
- Any confirmed external integrations.
