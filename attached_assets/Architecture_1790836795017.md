# AEGIS — Architecture

## 1. Architecture Objective
Build a responsive, accessible web/PWA experience for phone and tablet, with a modular backend that can evolve without forcing unnecessary data collection.

## 2. Proposed Stack
### Frontend
- Next.js / React
- TypeScript
- Tailwind CSS
- Accessible component primitives (for example, shadcn/ui/Radix where appropriate)
- React Hook Form + Zod for validated forms

### Backend
- Next.js server routes/server actions or a dedicated API layer.
- PostgreSQL for structured application data.
- Managed authentication only where required.
- Object storage only for explicitly required documents/assets.

### Infrastructure
- Managed cloud hosting.
- HTTPS everywhere.
- Environment variables/secrets manager.
- CI/CD with preview deployments.
- Automated linting, type checking and tests.

**Prototype principle:** use managed services to reduce custom infrastructure, but document every external processor.

## 4. Primary Product Flows
### Onboarding
1. Explain AEGIS.
2. Identify user role.
3. Collect minimum required information.
4. Display required privacy/data-use notice.
5. Obtain any necessary consent through separate, unbundled controls.
6. Configure trusted contacts and permissions.
7. Land on the simplified home screen.

### Daily Check-In
1. Reminder appears.
2. User taps or responds by voice.
3. Status is recorded.
4. If missed, execute configured escalation rule.
5. Log the event and acknowledgement.

### Help Request
1. User selects or says what they need.
2. AEGIS checks permissions and available services.
3. User reviews the request where appropriate.
4. Request is sent to an approved contact/provider.
5. Status is shown.
6. Family notification occurs only according to permission/rules.

### Emergency
1. User activates emergency/help control or an approved sensor creates an alert.
2. System validates the configured workflow.
3. Appropriate contact/service is notified.
4. Acknowledgement is tracked.
5. Escalation continues only according to predefined rules.

## 5. AI Boundary
AI may:
- Translate or simplify user requests.
- Help classify a service request.
- Generate a structured task from a natural-language request.
- Help explain non-clinical interface content.

AI must not:
- Diagnose disease.
- Prescribe medicine.
- Decide that an emergency is medically safe.
- Override user permissions.
- Invent provider information.
- Generate unsupported medical/safety claims.
- Make high-impact decisions without appropriate human oversight.

Critical workflows must have deterministic rules independent of AI availability.

## 6. Security Architecture
- Least-privilege access.
- Server-side authorization for protected operations.
- Secure session management.
- Input validation on every trusted boundary.
- Parameterized database queries/ORM protections.
- CSRF protections where applicable.
- Rate limiting on authentication and sensitive actions.
- Audit logging for security-sensitive events.
- Secrets never committed to source control.
- Separate development/staging/production environments.
- Regular dependency updates and vulnerability scanning.

## 7. Privacy Architecture
- Data minimisation.
- Purpose-based fields.
- Separate sensitive-data access from ordinary profile data.
- Role-based access for family/provider views.
- Consent records stored separately and auditably.
- Configurable retention/deletion workflows.
- No health data sent to general-purpose analytics.
- Third-party data flows documented before integration.

## 11. Third-Party Integration Rule
Every integration requires:
1. Business purpose.
2. Data inventory.
3. Privacy/security review.
4. Contract/terms review.
5. Consent assessment.
6. Failure fallback.
7. Removal plan.

## 12. Observability
Log operational events needed for reliability and security, but minimise personal content.

Track:
- Request IDs.
- Error codes.
- System latency.
- Job success/failure.
- Security events.
- Alert delivery status.

Avoid logging:
- Passwords.
- Tokens.
- Full health records.
- Sensitive form payloads.
- Authentication secrets.
