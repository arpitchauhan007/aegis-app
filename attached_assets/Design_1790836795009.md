# AEGIS — Design System & UI Specification

## 1. Design Direction
**Personality:** calm, trustworthy, warm, simple, protective.

The UI should feel closer to a familiar healthcare/service application than a futuristic technology product.

## 2. Primary Users
Adults/older adults approximately 40–70+, plus family members/caregivers.

Primary design priorities:
1. Understandability.
2. Readability.
3. Predictability.
4. Touch accuracy.
5. Confidence and reassurance.
6. Accessibility.
7. Low cognitive load.

## 3. Colour System

| Token | Hex | Purpose |
|---|---|---|
| Primary | `#4F7C78` | Main brand/action colour |
| Secondary | `#8FA89A` | Supporting accents |
| Background | `#F7F7F2` | Main page background |
| Surface | `#FFFFFF` | Cards and forms |
| Text Primary | `#172A32` | Main readable text |
| Text Secondary | `#52636A` | Supporting text |
| Success | `#3F7D58` | Completed/healthy state |
| Warning | `#B7791F` | Caution |
| Emergency | `#B83A3A` | Emergency/danger |

Use calm colours as the dominant palette. Saturated warning/emergency colours must be limited to appropriate states.

Do not communicate important meaning through colour alone.

## 4. Contrast
Engineering target:
- Normal text: at least 4.5:1.
- Large text: at least 3:1.
- Meaningful non-text UI components: at least 3:1.
- Focus indication must remain clearly visible.

Contrast must be tested with the actual rendered design, not only the hex values.

## 5. Typography
Preferred font families:
- Inter
- Noto Sans
- Roboto
- System sans-serif fallback

Recommended scale:
- Display/Page title: 28–32 px
- Section heading: 22–26 px
- Card heading: 18–22 px
- Body: 16–20 px
- Button label: 18–20 px
- Supporting text: 16–18 px

Avoid overly thin font weights.

## 6. Layout
- Spacious layout.
- Clear grouping.
- Short content blocks.
- One primary action per area when possible.
- No unnecessary visual clutter.
- Avoid long scrolling where a simple hierarchy can solve the problem.
- Tablet layout should use larger cards/columns without increasing cognitive complexity.

## 7. Components
### Buttons
- Height: typically 48–64 px.
- Clear text label.
- Icon optional but supportive.
- Primary action visually distinct.
- Destructive action clearly differentiated.

### Cards
Use cards for:
- Today.
- Family.
- Help.
- Services.
- Reminders.
- Alerts.

Each card should contain a clear title and one obvious next action.

### Navigation
Recommended:
- Home
- Family
- Help
- Services
- Profile

Emergency/help action remains visually prominent.

Avoid hiding core actions behind unfamiliar gestures.

## 8. Home Screen
The first screen should answer:
- What do I need to do today?
- Is my family reachable?
- Can I get help quickly?

Suggested hierarchy:
1. Greeting
2. Today
3. Family
4. Need Help?
5. Emergency / I Need Help
6. Upcoming reminder/appointment

Do not show every feature on the first screen.

## 9. Icons
Use familiar, literal icons with text:
- Phone + Call.
- Calendar + Appointments.
- Medicine + Medicines.
- Grocery bag + Groceries.
- House + Home.
- People + Family.
- Shield + Safety.
- Bell + Reminders.

Do not use an icon without a meaningful accessible name.

## 10. Forms
- Visible labels.
- Large inputs.
- High-contrast field borders.
- Clear focus state.
- Input purpose/autocomplete where appropriate.
- Error shown next to the relevant field.
- Errors written as corrective instructions.
- No placeholder-only labels.

## 11. Voice
Voice is optional and should supplement, not replace, visual controls.

Example intents:
- "Call my son."
- "I need groceries."
- "Remind me at six."
- "I need help."

Always provide visual confirmation of the interpreted action before consequential external actions where appropriate.

## 12. Motion
- Minimal.
- No decorative looping animations.
- No flashing.
- Respect reduced-motion preferences.
- Use animation only to communicate state changes or maintain orientation.

## 13. Imagery
Prefer:
- Authentic, licensed photography.
- Simple illustrations.
- Calm, relatable scenes.
- High-resolution assets.

Avoid:
- Stock images presented as real AEGIS users.
- Medical imagery used only for decoration.
- Images with unclear licensing.
- Visuals that imply unsupported clinical outcomes.

Every meaningful image must have appropriate alt text.

## 14. Accessibility
Target WCAG 2.2 AA.

Required:
- Keyboard support.
- Visible focus.
- Semantic HTML.
- Screen-reader labels.
- Alt text.
- Logical tab order.
- No colour-only status.
- Resize/reflow support.
- Clear error messages.
- Accessible modal/dialog behaviour.
- Accessible authentication.

## 15. Responsive Behaviour
### Phone
- Single-column layout.
- Large primary actions.
- Bottom or top navigation with labels.
- Minimal simultaneous information.

### Tablet
- Wider cards and two-column layouts where useful.
- Maintain large text and touch targets.
- Keep primary actions in consistent locations.

### Desktop
- Family/provider dashboards can become denser.
- The elder-facing experience should remain simple rather than becoming a complex enterprise dashboard.

## 16. UX Principles
- **Recognise, don't remember.**
- **One clear action at a time.**
- **Always show what happened.**
- **Never hide critical help.**
- **Use plain language.**
- **Make mistakes recoverable.**
- **Never punish the user for declining optional data sharing.**
- **Keep the user in control.**

## 17. Design QA
Every screen must be checked for:
- Contrast.
- Font size.
- Focus state.
- Keyboard operation.
- Touch target size.
- Label clarity.
- Screen-reader semantics.
- Error/empty/loading states.
- Responsive behaviour.
- Colour-only dependencies.
